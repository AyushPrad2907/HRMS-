    38→## 1. Introduction & Business Context
    39→
    40→Implex Edu currently manages employee work reporting, attendance, and leave through WhatsApp groups and shared Excel sheets. This is error-prone, unauditable, has no single source of truth, and does not scale past a handful of employees. As the company grows beyond its initial three functions — HR administration, teaching delivery, and marketing/sales — this manual process becomes a structural liability.
    41→
    42→This document specifies an enterprise-grade HRMS that centralizes:
    43→
    44→- Employee lifecycle management (onboarding, roles, offboarding)
    45→- Attendance tracking
    46→- Daily work reporting (role-specific)
    47→- Leave requests and approvals
    48→- Productivity and performance analytics
    49→- Realtime notifications
    50→- Full audit history of sensitive actions
    51→
    52→The system is designed so that **adding a new department (Sales, Accounts, Support, Content, Operations, Management) requires no architectural change** — only new role definitions, permission sets, and (optionally) a new report-type schema extension.

    86→## 3. Architectural Principles
    87→
    88→The system follows **Clean Architecture** adapted to Next.js's App Router, and **SOLID** principles at the module level:
    89→
    90→- **Single Responsibility** — each Server Action does one write; each Route Handler exposes one resource concern; UI components are presentation-only and receive data via props or Server Components.
    91→- **Open/Closed** — role-specific behavior (e.g., report forms) is implemented via a **strategy pattern**: a `ReportTypeDefinition` registry, not `if (role === 'teacher')` branching scattered across the codebase. Adding "Sales" reports means registering a new definition, not editing existing modules.
    92→- **Liskov Substitution** — all report types implement a common `ReportSubmission` interface so dashboards, exports, and analytics can treat any report generically.
    93→- **Interface Segregation** — permission checks are granular (`employee:create`, `leave:approve`) rather than coarse role checks, so UI and server logic depend only on the permissions they need.
    94→- **Dependency Inversion** — business logic (services layer) depends on repository interfaces, not directly on Prisma client calls, so the data layer can be tested/mocked and swapped if needed.
    95→
    96→**Role-independence rule:** No table, Server Action, or UI component may hard-code a role name in its core logic. Role names live only in seed data and permission-mapping tables. All access decisions route through the `permissions` / `role_permissions` tables.

   116→
   117→### 4.1 Explicitly Excluded
   118→
   119→Express.js, a standalone Node REST server, MongoDB/Mongoose, Vite, Render, Railway, Socket.io, Cloudinary, and NGINX are excluded by mandate — Next.js Route Handlers replace a REST server, Supabase Realtime replaces Socket.io, Supabase Storage replaces Cloudinary, and Vercel's edge network replaces NGINX. Redis is **not used in v1**; if a future need for shared caching or rate-limiting state arises beyond what Postgres/Vercel Edge Config can handle, it can be introduced without restructuring the app, but is not part of this design.

   192→
   193→```

   195→   ↓ calls

   207→## 6. Roles & Permission Model
   208→
   209→### 6.1 Design
   210→
   211→Permissions are **granular and additive**, stored in `permissions`, grouped into roles via `role_permissions`. The application never checks `role === 'hr'`; it checks `hasPermission(user, 'employee:create')`. This is what makes new departments pluggable — a new role is just a new row in `roles` plus a set of rows in `role_permissions`.
   212→
   213→### 6.2 Initial Role → Permission Matrix
   214→
   215→| Permission | HR Admin | Teacher | Marketing |
   216→|---|:---:|:---:|:---:|
   217→| `employee:create` | ✅ | ❌ | ❌ |
   218→| `employee:edit` | ✅ | ❌ (own profile only) | ❌ (own profile only) |
   219→| `employee:delete` | ✅ | ❌ | ❌ |
   220→| `employee:view_all` | ✅ | ❌ | ❌ |
   221→| `attendance:mark_own` | ✅ | ✅ | ✅ |
   222→| `attendance:view_all` | ✅ | ❌ | ❌ |
   223→| `attendance:override` | ✅ | ❌ | ❌ |
   224→| `report:submit_teacher` | ❌ | ✅ | ❌ |
   225→| `report:submit_marketing` | ❌ | ❌ | ✅ |
   226→| `report:view_own` | ✅ | ✅ | ✅ |
   227→| `report:view_all` | ✅ | ❌ | ❌ |
   228→| `leave:request` | ✅ | ✅ | ✅ |
   229→| `leave:approve` | ✅ | ❌ | ❌ |
   230→| `analytics:view_org` | ✅ | ❌ | ❌ |
   231→| `analytics:view_own` | ✅ | ✅ | ✅ |
   232→| `notification:broadcast` | ✅ | ❌ | ❌ |
   233→| `settings:manage` | ✅ | ❌ | ❌ |
   234→| `audit:view` | ✅ | ❌ | ❌ |
   235→
   236→Adding "Sales" later means: insert `role = 'sales'`, insert `report:submit_sales` permission, map it, and register a `SalesReportDefinition` in the report-type registry (Section 3). No existing table or Server Action changes.
   237→
   238→### 6.3 Permission Evaluation Order
   239→
   240→1. **Middleware** — is there a valid session? If not, redirect to `/login`.
   241→2. **Route-level guard** (layout-level, e.g., `/app/(hr)/layout.tsx`) — does the user hold *any* permission in this route group's required set? If not, 403 page.
   242→3. **Service-layer check** — does the user hold the *specific* permission for this action? If not, throw `ForbiddenError`.
   243→4. **Database RLS** — even if application logic is somehow bypassed, Postgres RLS policies (Section 8.4) independently enforce row-level access as the last line of defense.

   245→## 7. Database Design
   246→
   247→### 7.1 Conventions
   248→
   249→- Every table: `id UUID PRIMARY KEY DEFAULT gen_random_uuid()`, `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`, `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()` (maintained via trigger), `deleted_at TIMESTAMPTZ NULL` for soft delete.
   250→- Soft delete: application queries always filter `deleted_at IS NULL` via Prisma middleware; hard delete is restricted to a scheduled retention job (Section 13.7).
   251→- Foreign keys use `ON DELETE RESTRICT` by default, `ON DELETE CASCADE` only for strictly dependent child rows (e.g., `teacher_classes` rows under a `teacher_reports` row).
   252→- Naming: snake_case columns/tables (Postgres convention), camelCase in Prisma models (Prisma handles the mapping via `@map`/`@@map`).

   385→### 7.5 Prisma Model Architecture
   386→
   387→Prisma models mirror the tables above 1:1, organized into separate schema files stitched via `prisma.config` (`prisma/schema/*.prisma` with `previewFeatures = ["prismaSchemaFolder"]`) so the schema scales cleanly as departments are added:
   388→
   389→```
   390→prisma/schema/
   391→  identity.prisma      // User, Profile, Role, Permission, RolePermission, UserRole
   392→  employee.prisma       // Employee, Department, Attendance, Holiday
   393→  reports.prisma         // TeacherReport, TeacherClass, MarketingReport, MarketingMeeting, MarketingCall
   394→  crm.prisma              // MarketingLead, MarketingFollowup, MarketingDeal
   395→  leave.prisma            // LeaveRequest
   396→  system.prisma           // Notification, AuditLog, ActivityLog, Settings
   397→```
   398→
   399→Example excerpt (`employee.prisma`):
   400→
   401→```prisma
   402→model Employee {
   403→  id                   String   @id @default(uuid())
   404→  employeeCode         String   @unique @map("employee_code")
   405→  departmentId         String   @map("department_id")
   406→  designation          String
   407→  joinDate             DateTime @map("join_date") @db.Date
   408→  employmentStatus     String   @default("active") @map("employment_status")
   409→  reportingManagerId   String?  @map("reporting_manager_id")
   410→
   411→  department           Department @relation(fields: [departmentId], references: [id])
   412→  reportingManager     Employee?  @relation("ManagerReports", fields: [reportingManagerId], references: [id])
   413→  directReports        Employee[] @relation("ManagerReports")
   414→
   415→  attendance           Attendance[]
   416→  leaveRequests        LeaveRequest[]
   417→  teacherReports       TeacherReport[]
   418→  marketingReports     MarketingReport[]
   419→
   420→  createdAt            DateTime  @default(now()) @map("created_at")
   421→  updatedAt            DateTime  @updatedAt @map("updated_at")
   422→  deletedAt            DateTime? @map("deleted_at")
   423→
   424→  @@map("employees")
   425→}
   426→```

   428→Prisma Client is wrapped in a **soft-delete middleware** (`$extends`) so every model with a `deletedAt` field automatically excludes soft-deleted rows unless a query explicitly opts in with `includeDeleted: true`.

   430→## 8. Authentication & Authorization
   431→
   432→### 8.1 Authentication Flow
   433→
   434→- Supabase Auth handles email/password sign-in, email verification, and password reset out of the box.
   435→- On successful sign-in, Supabase issues a JWT (access token) + refresh token, stored in **httpOnly, secure cookies** via `@supabase/ssr`'s cookie adapter — never in `localStorage`.
   436→- Next.js **Middleware** runs on every request to refresh the session cookie and attach the resolved user to the request context.
   437→
   438→```mermaid
   439→flowchart LR
   440→    A[User submits credentials] --> B[Supabase Auth verifies]
   441→    B -->|success| C[JWT + refresh token issued]
   442→    C --> D[Set httpOnly cookies via @supabase/ssr]
   443→    D --> E[Middleware validates on each request]
   444→    E --> F{Session valid?}
   445→    F -->|yes| G[Attach user + roles to request]
   446→    F -->|no| H[Redirect to /login]
   447→```
   448→
   449→### 8.2 Email Verification & Password Reset
   450→
   451→- New employees are created by HR via a Server Action that calls `supabase.auth.admin.inviteUserByEmail()`, sending a Supabase-hosted invite email; the employee sets their password on first login.
   452→- Password reset uses `supabase.auth.resetPasswordForEmail()`, landing on a dedicated `/reset-password` route that verifies the recovery token before allowing a new password (Zod-validated for strength).
   453→
   454→### 8.3 Route Protection
   455→
   456→- `middleware.ts` matches all routes except static assets and `/login`, `/reset-password`.
   457→- Route groups encode required permission sets: `/app/(hr)/**`, `/app/(teacher)/**`, `/app/(marketing)/**`, with a shared `/app/(shared)/**` for profile/notifications.
   458→- Each route group's `layout.tsx` performs the Section 6.3 step-2 guard server-side (before any UI renders), preventing any flash-of-protected-content.
   459→
   460→### 8.4 Row Level Security (RLS) Strategy
   461→
   462→RLS is **defense-in-depth**, not the primary authorization mechanism (that's the service layer) — but it is mandatory on every table so a bug in application code cannot leak data.
   463→
   464→General pattern:
   465→
   466→```sql
   467→alter table public.leave_requests enable row level security;
   468→
   469→-- Employees can see their own leave requests
   470→create policy "employees_select_own_leave"
   471→on public.leave_requests for select
   472→using (employee_id = auth.uid());
   473→
   474→-- HR (or anyone holding leave:approve) can see and update all
   475→create policy "hr_manage_all_leave"
   476→on public.leave_requests for all
   477→using (
   478→  exists (
   479→    select 1 from user_roles ur
   480→    join role_permissions rp on rp.role_id = ur.role_id
   481→    join permissions p on p.id = rp.permission_id
   482→    where ur.user_id = auth.uid()
   483→      and p.name = 'leave:approve'
   484→  )
   485→);
   486→```
   487→
   488→This same `has_permission(auth.uid(), 'permission:name')` check is wrapped as a Postgres **SQL function** (`security definer`) and reused across every policy to avoid duplicating the join logic per table:
   489→
   490→```sql
   491→create or replace function has_permission(uid uuid, perm text)
   492→returns boolean
   493→language sql security definer stable as $$
   494→  select exists (
   495→    select 1 from user_roles ur
   496→    join role_permissions rp on rp.role_id = ur.role_id
   497→    join permissions p on p.id = rp.permission_id
   498→    where ur.user_id = uid and p.name = perm
   499→  );
   500→$$;
   501→```
   502→
   503→Policies then read as `using (has_permission(auth.uid(), 'employee:view_all') or employee_id = auth.uid())`.
   504→
   505→### 8.5 How Auth, Authorization, and DB Permissions Compose
   506→
   507→| Layer | Question it answers | Mechanism |
   508→|---|---|---|
   509→| Authentication | "Who are you?" | Supabase Auth JWT, verified in Middleware |
   510→| Route Guard | "Can you even be here?" | Layout-level permission-set check |
   511→| Authorization (service) | "Can you do *this specific action*?" | `hasPermission(user, 'resource:action')` in service layer |
   512→| RLS (DB) | "Even if everything above is bypassed, can this SQL statement touch this row?" | Postgres policies using `has_permission()` |
   513→
   514→All four layers must agree; RLS is intentionally the strictest and final gate.

   603→## 13. Security Architecture
   604→
   605→| Concern | Mitigation |
   606→|---|---|
   607→| OWASP A01 Broken Access Control | 4-layer authorization (Section 8.5); RLS on every table |
   608→| OWASP A02 Cryptographic Failures | TLS everywhere (Vercel/Supabase enforced); secrets never in client bundle |
   609→| OWASP A03 Injection | Prisma parameterizes all queries; zero raw string SQL concatenation; Zod validates all input shape/type before it reaches Prisma |
   610→| XSS | React's default escaping; no `dangerouslySetInnerHTML` except for a sanitized (DOMPurify) rich-text renderer if notes support formatting |
   611→| CSRF | Server Actions use Next.js's built-in origin-checking; state-changing Route Handlers require same-site cookies + explicit origin header check |
   612→| File Upload Security | File type allow-list, size limits, virus-scan hook placeholder, storage bucket policies (Section 14) |
   613→| Secrets Management | All keys in Vercel Environment Variables (per-environment: dev/preview/prod); `SUPABASE_SERVICE_ROLE_KEY` used **only** in trusted server contexts, never exposed to client |
   614→| Audit Logging | Immutable `audit_logs` table (Section 7.4), DB-level `REVOKE UPDATE, DELETE` |
   615→| Rate Limiting | Vercel Edge Middleware + Supabase built-in Auth rate limits on login/reset endpoints |
   616→| Data Retention | Soft-deleted rows purged by a scheduled job only after a configurable retention window, itself audit-logged |

   639→## 15. Realtime Notifications
   640→
   641→### 15.1 Delivery Mechanism
   642→
   643→`notifications` table insert → Supabase Realtime (Postgres CDC via logical replication) → client subscribes to a **per-user filtered channel** (`notifications:employee_id=eq.<uid>`) → toast + notification-bell badge update, no polling.
   644→
   645→```mermaid
   646→sequenceDiagram
   647→    participant SVC as Service Layer
   648→    participant DB as notifications table
   649→    participant RT as Supabase Realtime
   650→    participant UI as Recipient Browser
   651→
   652→    SVC->>DB: INSERT notification (recipient, type, payload)
   653→    DB-->>RT: Change event (CDC)
   654→    RT-->>UI: Push via WebSocket (subscribed channel)
   655→    UI->>UI: Update bell badge + optional toast
   656→```
   657→
   658→### 15.2 Notification Types
   659→
   660→| Type | Trigger | Recipient(s) |
   661→|---|---|---|
   662→| `leave.approved` / `leave.rejected` | HR decision on a leave request | Requesting employee |
   663→| `leave.requested` | Employee submits leave | HR holders of `leave:approve` |
   664→| `report.reminder` | Scheduled job (e.g., 6 PM) if no report submitted | Employee who hasn't reported |
   665→| `employee.created` | New employee onboarded | HR team, new employee's manager |
   666→| `announcement` | HR broadcast composer | Targeted role/department, or org-wide |
   667→| `system.alert` | Operational issues (rare, admin-triggered) | HR Admins |
   668→
   669→Scheduled notifications (e.g., report reminders) are generated by a **Vercel Cron** job hitting a protected Route Handler that queries for employees without a report for the current date and inserts `notifications` rows — Realtime delivery is identical to the direct-insert path.

   685→### 16.2 Query Optimization Strategy
   686→
   687→- **Materialized Postgres views** for expensive aggregations that don't need to-the-second freshness (e.g., `mv_monthly_department_attendance`), refreshed via a nightly Vercel Cron → Route Handler → `REFRESH MATERIALIZED VIEW CONCURRENTLY`.
   688→- **Indexed date columns** (`attendance_date`, `report_date`, `closed_at`) on all reporting tables — every analytics query filters by a date range first.
   689→- **Partial indexes** for common filters, e.g. `CREATE INDEX ON leave_requests (status) WHERE status = 'pending'` to keep the HR approval queue query fast regardless of historical leave volume.
   690→- Heavy dashboard queries are executed via **Prisma raw SQL** (`$queryRaw`) against the views/indexes above rather than doing aggregation in application code — push computation to Postgres.
   691→- Recharts components receive **pre-aggregated** data from Server Components (fetched via the service/repository layer), never raw row-level data shipped to the client.

   693→## 17. Deployment Architecture & CI/CD
   694→
   695→### 17.1 Environment Flow
   696→
   697→```mermaid
   698→flowchart LR
   699→    Dev["Local Dev\n(Next.js + local Supabase CLI)"] -->|git push branch| GH[GitHub]
   700→    GH -->|PR opened| CI["GitHub Actions CI\n(lint, typecheck, unit, Playwright)"]
   701→    CI -->|pass| PV["Vercel Preview Deployment\n+ Supabase branch DB"]
   702→    PV -->|reviewed & merged to main| PROD["Vercel Production Deployment"]
   703→    PROD --> SUPA["Supabase Production Project"]
   704→```
   705→
   706→### 17.2 Local Development
   707→
   708→- Supabase CLI (`supabase start`) runs a local Postgres + Auth + Storage stack in Docker, mirroring production.
   709→- `prisma migrate dev` applies migrations locally; `prisma db seed` loads roles/permissions/demo data.
   710→- `.env.local` holds local Supabase URL/keys; never committed (`.gitignore`).
   711→
   712→### 17.3 Preview Deployments
   713→
   714→- Every PR triggers a Vercel Preview build **and** a corresponding Supabase preview branch (Supabase's database branching), so each PR gets an isolated database matching the PR's migration state — no shared staging drift.
   715→
   716→### 17.4 Production Deployment
   717→
   718→- Merge to `main` triggers Vercel production build.
   719→- `prisma migrate deploy` runs as a build step (or a gated GitHub Actions job before deploy) against the production `DIRECT_URL`, applying only already-reviewed migration files.
   720→- Migrations are **additive-first**: destructive changes (drop column, etc.) ship in a follow-up release after the code no longer references the old shape, avoiding downtime.
   721→
   722→### 17.5 CI/CD Pipeline (GitHub Actions)
   723→
   724→| Stage | Action |
   725→|---|---|
   726→| Lint & Typecheck | `eslint`, `tsc --noEmit` |
   727→| Unit/Component Tests | `jest` + React Testing Library |
   728→| E2E Tests | `playwright test` against a Preview Deployment URL |
   729→| Migration Check | `prisma migrate diff` to catch drift between schema and migration files |
   730→| Deploy | Vercel auto-deploys on merge (native GitHub integration); Actions gate the merge, not the deploy itself |
   731→
   732→### 17.6 Rollback Strategy
   733→
   734→- Vercel: instant rollback to any previous production deployment via the dashboard/CLI (atomic, no rebuild needed).
   735→- Database: because migrations are additive-first, a code rollback rarely requires a DB rollback; when a schema rollback is unavoidable, a paired "down" migration is authored and reviewed before the risky migration ships.
   736→
   737→### 17.7 Backup Strategy
   738→
   739→- Supabase automated daily backups (Point-in-Time Recovery on paid tiers) for the production project.
   740→- Weekly `pg_dump` exported to a separate storage location as an out-of-band backup, retained on a rolling 90-day window.
