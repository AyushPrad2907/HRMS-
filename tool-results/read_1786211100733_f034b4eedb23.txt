    38→    38→## 1. Introduction & Business Context
    39→    39→
    40→    40→Implex Edu currently manages employee work reporting, attendance, and leave through WhatsApp groups and shared Excel sheets. This is error-prone, unauditable, has no single source of truth, and does not scale past a handful of employees. As the company grows beyond its initial three functions — HR administration, teaching delivery, and marketing/sales — this manual process becomes a structural liability.
    41→    41→
    42→    42→This document specifies an enterprise-grade HRMS that centralizes:
    43→    43→
    44→    44→- Employee lifecycle management (onboarding, roles, offboarding)
    45→    45→- Attendance tracking
    46→    46→- Daily work reporting (role-specific)
    47→    47→- Leave requests and approvals
    48→    48→- Productivity and performance analytics
    49→    49→- Realtime notifications
    50→    50→- Full audit history of sensitive actions
    51→    51→
    52→    52→The system is designed so that **adding a new department (Sales, Accounts, Support, Content, Operations, Management) requires no architectural change** — only new role definitions, permission sets, and (optionally) a new report-type schema extension.

    86→    86→## 3. Architectural Principles
    87→    87→
    88→    88→The system follows **Clean Architecture** adapted to Next.js's App Router, and **SOLID** principles at the module level:
    89→    89→
    90→    90→- **Single Responsibility** — each Server Action does one write; each Route Handler exposes one resource concern; UI components are presentation-only and receive data via props or Server Components.
    91→    91→- **Open/Closed** — role-specific behavior (e.g., report forms) is implemented via a **strategy pattern**: a `ReportTypeDefinition` registry, not `if (role === 'teacher')` branching scattered across the codebase. Adding "Sales" reports means registering a new definition, not editing existing modules.
    92→    92→- **Liskov Substitution** — all report types implement a common `ReportSubmission` interface so dashboards, exports, and analytics can treat any report generically.
    93→    93→- **Interface Segregation** — permission checks are granular (`employee:create`, `leave:approve`) rather than coarse role checks, so UI and server logic depend only on the permissions they need.
    94→    94→- **Dependency Inversion** — business logic (services layer) depends on repository interfaces, not directly on Prisma client calls, so the data layer can be tested/mocked and swapped if needed.
    95→    95→
    96→    96→**Role-independence rule:** No table, Server Action, or UI component may hard-code a role name in its core logic. Role names live only in seed data and permission-mapping tables. All access decisions route through the `permissions` / `role_permissions` tables.

   100→   100→| Layer | Technology | Why |

   103→   103→| Language | TypeScript | End-to-end type safety from DB (Prisma) → service layer → UI |

   105→   105→| Icons | Lucide Icons | Consistent, tree-shakeable icon set matching Shadcn's design language |
   106→   106→| Charts | Recharts | Composable, SVG-based, good default for HR/analytics dashboards |
   107→   107→| Motion | Framer Motion | Micro-interactions (dashboard transitions, modals, skeleton fades) |
   108→   108→| Forms | React Hook Form + Zod | Performant uncontrolled forms + schema validation reused on client **and** server (same Zod schema imported into Server Actions) |
   109→   109→| Database | Supabase PostgreSQL | Managed Postgres with built-in RLS, Auth, Storage, Realtime under one vendor |
   110→   110→| ORM | Prisma | Type-safe query layer, migrations, and schema-as-code; used for all non-RLS-sensitive access |
   111→   111→| Auth | Supabase Auth | Email/password, email verification, password reset, JWT session cookies, integrates directly with Postgres RLS via `auth.uid()` |
   112→   112→| Storage | Supabase Storage | Bucket-based file storage with policy-based access control, same project as DB/Auth |
   113→   113→| Realtime | Supabase Realtime | Postgres logical replication → websocket push, used for notifications |
   114→   114→| Deployment | Vercel + Supabase | Zero-ops hosting; Vercel Preview Deployments per PR; Supabase branching for DB previews |
   115→   115→| Testing | Jest, React Testing Library, Playwright | Unit/component tests + full E2E coverage of critical flows |
   116→   116→
   117→   117→### 4.1 Explicitly Excluded
   118→   118→
   119→   119→Express.js, a standalone Node REST server, MongoDB/Mongoose, Vite, Render, Railway, Socket.io, Cloudinary, and NGINX are excluded by mandate — Next.js Route Handlers replace a REST server, Supabase Realtime replaces Socket.io, Supabase Storage replaces Cloudinary, and Vercel's edge network replaces NGINX. Redis is **not used in v1**; if a future need for shared caching or rate-limiting state arises beyond what Postgres/Vercel Edge Config can handle, it can be introduced without restructuring the app, but is not part of this design.

   191→   191→### 5.3 Layering Within the Next.js App
   192→   192→
   193→   193→```
   194→   194→UI (Server/Client Components)
   195→   195→   ↓ calls
   196→   196→Server Actions / Route Handlers   (thin — validation + orchestration only)
   197→   197→   ↓ calls
   198→   198→Service Layer (/lib/services/*)   (business rules, permission checks)
   199→   199→   ↓ calls
   200→   200→Repository Layer (/lib/repositories/*) (Prisma queries, isolated per aggregate)
   201→   201→   ↓ queries

   205→   205→Server Actions and Route Handlers never call Prisma directly for anything beyond trivial reads — all writes and permission-sensitive reads go through the service layer so business rules live in one place and are unit-testable without spinning up Next.js.

   207→   207→## 6. Roles & Permission Model
   208→   208→
   209→   209→### 6.1 Design
   210→   210→
   211→   211→Permissions are **granular and additive**, stored in `permissions`, grouped into roles via `role_permissions`. The application never checks `role === 'hr'`; it checks `hasPermission(user, 'employee:create')`. This is what makes new departments pluggable — a new role is just a new row in `roles` plus a set of rows in `role_permissions`.
   212→   212→
   213→   213→### 6.2 Initial Role → Permission Matrix
   214→   214→
   215→   215→| Permission | HR Admin | Teacher | Marketing |
   216→   216→|---|:---:|:---:|:---:|
   217→   217→| `employee:create` | ✅ | ❌ | ❌ |
   218→   218→| `employee:edit` | ✅ | ❌ (own profile only) | ❌ (own profile only) |
   219→   219→| `employee:delete` | ✅ | ❌ | ❌ |
   220→   220→| `employee:view_all` | ✅ | ❌ | ❌ |
   221→   221→| `attendance:mark_own` | ✅ | ✅ | ✅ |
   222→   222→| `attendance:view_all` | ✅ | ❌ | ❌ |
   223→   223→| `attendance:override` | ✅ | ❌ | ❌ |
   224→   224→| `report:submit_teacher` | ❌ | ✅ | ❌ |
   225→   225→| `report:submit_marketing` | ❌ | ❌ | ✅ |
   226→   226→| `report:view_own` | ✅ | ✅ | ✅ |
   227→   227→| `report:view_all` | ✅ | ❌ | ❌ |

   235→   235→
   236→   236→Adding "Sales" later means: insert `role = 'sales'`, insert `report:submit_sales` permission, map it, and register a `SalesReportDefinition` in the report-type registry (Section 3). No existing table or Server Action changes.
   237→   237→
   238→   238→### 6.3 Permission Evaluation Order
   239→   239→
   240→   240→1. **Middleware** — is there a valid session? If not, redirect to `/login`.
   241→   241→2. **Route-level guard** (layout-level, e.g., `/app/(hr)/layout.tsx`) — does the user hold *any* permission in this route group's required set? If not, 403 page.
   242→   242→3. **Service-layer check** — does the user hold the *specific* permission for this action? If not, throw `ForbiddenError`.
   243→   243→4. **Database RLS** — even if application logic is somehow bypassed, Postgres RLS policies (Section 8.4) independently enforce row-level access as the last line of defense.

   245→   245→## 7. Database Design
   246→   246→
   247→   247→### 7.1 Conventions
   248→   248→
   249→   249→- Every table: `id UUID PRIMARY KEY DEFAULT gen_random_uuid()`, `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`, `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()` (maintained via trigger), `deleted_at TIMESTAMPTZ NULL` for soft delete.
   250→   250→- Soft delete: application queries always filter `deleted_at IS NULL` via Prisma middleware; hard delete is restricted to a scheduled retention job (Section 13.7).
   251→   251→- Foreign keys use `ON DELETE RESTRICT` by default, `ON DELETE CASCADE` only for strictly dependent child rows (e.g., `teacher_classes` rows under a `teacher_reports` row).
   252→   252→- Naming: snake_case columns/tables (Postgres convention), camelCase in Prisma models (Prisma handles the mapping via `@map`/`@@map`).

   369→   369→**`audit_logs`** (append-only, no `updated_at`/soft delete — immutable by design)

   372→   372→|---|---|

   430→   430→## 8. Authentication & Authorization
   431→   431→
   432→   432→### 8.1 Authentication Flow
   433→   433→
   434→   434→- Supabase Auth handles email/password sign-in, email verification, and password reset out of the box.
   435→   435→- On successful sign-in, Supabase issues a JWT (access token) + refresh token, stored in **httpOnly, secure cookies** via `@supabase/ssr`'s cookie adapter — never in `localStorage`.
   436→   436→- Next.js **Middleware** runs on every request to refresh the session cookie and attach the resolved user to the request context.
   437→   437→
   438→   438→```mermaid
   439→   439→flowchart LR
   440→   440→    A[User submits credentials] --> B[Supabase Auth verifies]
   441→   441→    B -->|success| C[JWT + refresh token issued]
   442→   442→    C --> D[Set httpOnly cookies via @supabase/ssr]
   443→   443→    D --> E[Middleware validates on each request]
   444→   444→    E --> F{Session valid?}
   445→   445→    F -->|yes| G[Attach user + roles to request]
   446→   446→    F -->|no| H[Redirect to /login]
   447→   447→```
   448→   448→
   449→   449→### 8.2 Email Verification & Password Reset
   450→   450→
   451→   451→- New employees are created by HR via a Server Action that calls `supabase.auth.admin.inviteUserByEmail()`, sending a Supabase-hosted invite email; the employee sets their password on first login.
   452→   452→- Password reset uses `supabase.auth.resetPasswordForEmail()`, landing on a dedicated `/reset-password` route that verifies the recovery token before allowing a new password (Zod-validated for strength).
   453→   453→
   454→   454→### 8.3 Route Protection
   455→   455→
   456→   456→- `middleware.ts` matches all routes except static assets and `/login`, `/reset-password`.
   457→   457→- Route groups encode required permission sets: `/app/(hr)/**`, `/app/(teacher)/**`, `/app/(marketing)/**`, with a shared `/app/(shared)/**` for profile/notifications.
   458→   458→- Each route group's `layout.tsx` performs the Section 6.3 step-2 guard server-side (before any UI renders), preventing any flash-of-protected-content.
   459→   459→
   460→   460→### 8.4 Row Level Security (RLS) Strategy
   461→   461→
   462→   462→RLS is **defense-in-depth**, not the primary authorization mechanism (that's the service layer) — but it is mandatory on every table so a bug in application code cannot leak data.
   463→   463→
   464→   464→General pattern:
   465→   465→
   466→   466→```sql
   467→   467→alter table public.leave_requests enable row level security;
   468→   468→
   469→   469→-- Employees can see their own leave requests
   470→   470→create policy "employees_select_own_leave"
   471→   471→on public.leave_requests for select
   472→   472→using (employee_id = auth.uid());
   473→   473→
   474→   474→-- HR (or anyone holding leave:approve) can see and update all
   475→   475→create policy "hr_manage_all_leave"
   476→   476→on public.leave_requests for all
   477→   477→using (
   478→   478→  exists (
   479→   479→    select 1 from user_roles ur
   480→   480→    join role_permissions rp on rp.role_id = ur.role_id
   481→   481→    join permissions p on p.id = rp.permission_id
   482→   482→    where ur.user_id = auth.uid()
   483→   483→      and p.name = 'leave:approve'
   484→   484→  )
   485→   485→);
   486→   486→```
   487→   487→
   488→   488→This same `has_permission(auth.uid(), 'permission:name')` check is wrapped as a Postgres **SQL function** (`security definer`) and reused across every policy to avoid duplicating the join logic per table:
   489→   489→
   490→   490→```sql
   491→   491→create or replace function has_permission(uid uuid, perm text)
   492→   492→returns boolean
   493→   493→language sql security definer stable as $$
   494→   494→  select exists (
   495→   495→    select 1 from user_roles ur
   496→   496→    join role_permissions rp on rp.role_id = ur.role_id
   497→   497→    join permissions p on p.id = rp.permission_id
   498→   498→    where ur.user_id = uid and p.name = perm
   499→   499→  );
   500→   500→$$;
   501→   501→```
   502→   502→
   503→   503→Policies then read as `using (has_permission(auth.uid(), 'employee:view_all') or employee_id = auth.uid())`.
   504→   504→
   505→   505→### 8.5 How Auth, Authorization, and DB Permissions Compose
   506→   506→
   507→   507→| Layer | Question it answers | Mechanism |
   508→   508→|---|---|---|
   509→   509→| Authentication | "Who are you?" | Supabase Auth JWT, verified in Middleware |
   510→   510→| Route Guard | "Can you even be here?" | Layout-level permission-set check |
   511→   511→| Authorization (service) | "Can you do *this specific action*?" | `hasPermission(user, 'resource:action')` in service layer |
   512→   512→| RLS (DB) | "Even if everything above is bypassed, can this SQL statement touch this row?" | Postgres policies using `has_permission()` |
   513→   513→
   514→   514→All four layers must agree; RLS is intentionally the strictest and final gate.

   603→   603→## 13. Security Architecture
   604→   604→
   605→   605→| Concern | Mitigation |
   606→   606→|---|---|
   607→   607→| OWASP A01 Broken Access Control | 4-layer authorization (Section 8.5); RLS on every table |
   608→   608→| OWASP A02 Cryptographic Failures | TLS everywhere (Vercel/Supabase enforced); secrets never in client bundle |
   609→   609→| OWASP A03 Injection | Prisma parameterizes all queries; zero raw string SQL concatenation; Zod validates all input shape/type before it reaches Prisma |
   610→   610→| XSS | React's default escaping; no `dangerouslySetInnerHTML` except for a sanitized (DOMPurify) rich-text renderer if notes support formatting |
   611→   611→| CSRF | Server Actions use Next.js's built-in origin-checking; state-changing Route Handlers require same-site cookies + explicit origin header check |
   612→   612→| File Upload Security | File type allow-list, size limits, virus-scan hook placeholder, storage bucket policies (Section 14) |
   613→   613→| Secrets Management | All keys in Vercel Environment Variables (per-environment: dev/preview/prod); `SUPABASE_SERVICE_ROLE_KEY` used **only** in trusted server contexts, never exposed to client |
   614→   614→| Audit Logging | Immutable `audit_logs` table (Section 7.4), DB-level `REVOKE UPDATE, DELETE` |
   615→   615→| Rate Limiting | Vercel Edge Middleware + Supabase built-in Auth rate limits on login/reset endpoints |
   616→   616→| Data Retention | Soft-deleted rows purged by a scheduled job only after a configurable retention window, itself audit-logged |

   685→   685→### 16.2 Query Optimization Strategy
   686→   686→
   687→   687→- **Materialized Postgres views** for expensive aggregations that don't need to-the-second freshness (e.g., `mv_monthly_department_attendance`), refreshed via a nightly Vercel Cron → Route Handler → `REFRESH MATERIALIZED VIEW CONCURRENTLY`.
   688→   688→- **Indexed date columns** (`attendance_date`, `report_date`, `closed_at`) on all reporting tables — every analytics query filters by a date range first.
   689→   689→- **Partial indexes** for common filters, e.g. `CREATE INDEX ON leave_requests (status) WHERE status = 'pending'` to keep the HR approval queue query fast regardless of historical leave volume.
   690→   690→- Heavy dashboard queries are executed via **Prisma raw SQL** (`$queryRaw`) against the views/indexes above rather than doing aggregation in application code — push computation to Postgres.
   691→   691→- Recharts components receive **pre-aggregated** data from Server Components (fetched via the service/repository layer), never raw row-level data shipped to the client.

   694→   694→
   695→   695→### 17.1 Environment Flow
   696→   696→
   697→   697→```mermaid
   698→   698→flowchart LR
   699→   699→    Dev["Local Dev\n(Next.js + local Supabase CLI)"] -->|git push branch| GH[GitHub]
   700→   700→    GH -->|PR opened| CI["GitHub Actions CI\n(lint, typecheck, unit, Playwright)"]
   701→   701→    CI -->|pass| PV["Vercel Preview Deployment\n+ Supabase branch DB"]
   702→   702→    PV -->|reviewed & merged to main| PROD["Vercel Production Deployment"]
   703→   703→    PROD --> SUPA["Supabase Production Project"]
   704→   704→```
   705→   705→
   706→   706→### 17.2 Local Development
   707→   707→
   708→   708→- Supabase CLI (`supabase start`) runs a local Postgres + Auth + Storage stack in Docker, mirroring production.
   709→   709→- `prisma migrate dev` applies migrations locally; `prisma db seed` loads roles/permissions/demo data.
   710→   710→- `.env.local` holds local Supabase URL/keys; never committed (`.gitignore`).
   711→   711→
   712→   712→### 17.3 Preview Deployments
   713→   713→
   714→   714→- Every PR triggers a Vercel Preview build **and** a corresponding Supabase preview branch (Supabase's database branching), so each PR gets an isolated database matching the PR's migration state — no shared staging drift.
   715→   715→
   716→   716→### 17.4 Production Deployment
   717→   717→
   718→   718→- Merge to `main` triggers Vercel production build.
   719→   719→- `prisma migrate deploy` runs as a build step (or a gated GitHub Actions job before deploy) against the production `DIRECT_URL`, applying only already-reviewed migration files.
   720→   720→- Migrations are **additive-first**: destructive changes (drop column, etc.) ship in a follow-up release after the code no longer references the old shape, avoiding downtime.
   721→   721→
   722→   722→### 17.5 CI/CD Pipeline (GitHub Actions)
   723→   723→
   724→   724→| Stage | Action |
   725→   725→|---|---|
   726→   726→| Lint & Typecheck | `eslint`, `tsc --noEmit` |
   727→   727→| Unit/Component Tests | `jest` + React Testing Library |
   728→   728→| E2E Tests | `playwright test` against a Preview Deployment URL |
   729→   729→| Migration Check | `prisma migrate diff` to catch drift between schema and migration files |
   730→   730→| Deploy | Vercel auto-deploys on merge (native GitHub integration); Actions gate the merge, not the deploy itself |
   731→   731→
   732→   732→### 17.6 Rollback Strategy
   733→   733→
   734→   734→- Vercel: instant rollback to any previous production deployment via the dashboard/CLI (atomic, no rebuild needed).
   735→   735→- Database: because migrations are additive-first, a code rollback rarely requires a DB rollback; when a schema rollback is unavoidable, a paired "down" migration is authored and reviewed before the risky migration ships.
   736→   736→
   737→   737→### 17.7 Backup Strategy
   738→   738→
   739→   739→- Supabase automated daily backups (Point-in-Time Recovery on paid tiers) for the production project.
   740→   740→- Weekly `pg_dump` exported to a separate storage location as an out-of-band backup, retained on a rolling 90-day window.

   815→   815→## 19. Testing Strategy
   816→   816→
   817→   817→| Layer | Tool | Coverage Target |
   818→   818→|---|---|---|
   819→   819→| Unit (services, permission logic, Zod schemas) | Jest | ≥ 80% on `lib/services` and `lib/validation` |
   820→   820→| Component | React Testing Library | Critical shared components (Data Table, forms, Command Palette) |
   821→   821→| Integration | Jest + a test Supabase branch | Server Actions against a real (ephemeral) Postgres instance |
   822→   822→| E2E | Playwright | Login → role-based dashboard load, employee CRUD, leave request → approval → notification, teacher/marketing report submission |
   823→   823→
   824→   824→E2E suites run against Vercel Preview Deployments in CI (Section 17.5), so every PR is validated end-to-end before merge.
