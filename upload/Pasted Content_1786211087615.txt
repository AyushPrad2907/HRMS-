## 1. Introduction & Business Context

Implex Edu currently manages employee work reporting, attendance, and leave through WhatsApp groups and shared Excel sheets. This is error-prone, unauditable, has no single source of truth, and does not scale past a handful of employees. As the company grows beyond its initial three functions — HR administration, teaching delivery, and marketing/sales — this manual process becomes a structural liability.

This document specifies an enterprise-grade HRMS that centralizes:

- Employee lifecycle management (onboarding, roles, offboarding)
- Attendance tracking
- Daily work reporting (role-specific)
- Leave requests and approvals
- Productivity and performance analytics
- Realtime notifications
- Full audit history of sensitive actions

The system is designed so that **adding a new department (Sales, Accounts, Support, Content, Operations, Management) requires no architectural change** — only new role definitions, permission sets, and (optionally) a new report-type schema extension.

## 3. Architectural Principles

The system follows **Clean Architecture** adapted to Next.js's App Router, and **SOLID** principles at the module level:

- **Single Responsibility** — each Server Action does one write; each Route Handler exposes one resource concern; UI components are presentation-only and receive data via props or Server Components.
- **Open/Closed** — role-specific behavior (e.g., report forms) is implemented via a **strategy pattern**: a `ReportTypeDefinition` registry, not `if (role === 'teacher')` branching scattered across the codebase. Adding "Sales" reports means registering a new definition, not editing existing modules.
- **Liskov Substitution** — all report types implement a common `ReportSubmission` interface so dashboards, exports, and analytics can treat any report generically.
- **Interface Segregation** — permission checks are granular (`employee:create`, `leave:approve`) rather than coarse role checks, so UI and server logic depend only on the permissions they need.
- **Dependency Inversion** — business logic (services layer) depends on repository interfaces, not directly on Prisma client calls, so the data layer can be tested/mocked and swapped if needed.

**Role-independence rule:** No table, Server Action, or UI component may hard-code a role name in its core logic. Role names live only in seed data and permission-mapping tables. All access decisions route through the `permissions` / `role_permissions` tables.

Express.js, a standalone Node REST server, MongoDB/Mongoose, Vite, Render, Railway, Socket.io, Cloudinary, and NGINX are excluded by mandate — Next.js Route Handlers replace a REST server, Supabase Realtime replaces Socket.io, Supabase Storage replaces Cloudinary, and Vercel's edge network replaces NGINX. Redis is **not used in v1**; if a future need for shared caching or rate-limiting state arises beyond what Postgres/Vercel Edge Config can handle, it can be introduced without restructuring the app, but is not part of this design.

### 5.3 Layering Within the Next.js App

```

   ↓ calls
Server Actions / Route Handlers   (thin — validation + orchestration only)
   ↓ calls
Service Layer (/lib/services/*)   (business rules, permission checks)
   ↓ calls
Repository Layer (/lib/repositories/*) (Prisma queries, isolated per aggregate)
   ↓ queries
Prisma Client → PostgreSQL (RLS as defense-in-depth)
```

Server Actions and Route Handlers never call Prisma directly for anything beyond trivial reads — all writes and permission-sensitive reads go through the service layer so business rules live in one place and are unit-testable without spinning up Next.js.

## 6. Roles & Permission Model

### 6.1 Design

Permissions are **granular and additive**, stored in `permissions`, grouped into roles via `role_permissions`. The application never checks `role === 'hr'`; it checks `hasPermission(user, 'employee:create')`. This is what makes new departments pluggable — a new role is just a new row in `roles` plus a set of rows in `role_permissions`.

### 6.2 Initial Role → Permission Matrix

| Permission | HR Admin | Teacher | Marketing |
|---|:---:|:---:|:---:|
| `employee:create` | ✅ | ❌ | ❌ |
| `employee:edit` | ✅ | ❌ (own profile only) | ❌ (own profile only) |
| `employee:delete` | ✅ | ❌ | ❌ |
| `employee:view_all` | ✅ | ❌ | ❌ |
| `attendance:mark_own` | ✅ | ✅ | ✅ |
| `attendance:view_all` | ✅ | ❌ | ❌ |
| `attendance:override` | ✅ | ❌ | ❌ |
| `report:submit_teacher` | ❌ | ✅ | ❌ |
| `report:submit_marketing` | ❌ | ❌ | ✅ |
| `report:view_own` | ✅ | ✅ | ✅ |
| `report:view_all` | ✅ | ❌ | ❌ |
| `leave:request` | ✅ | ✅ | ✅ |
| `leave:approve` | ✅ | ❌ | ❌ |
| `analytics:view_org` | ✅ | ❌ | ❌ |
| `analytics:view_own` | ✅ | ✅ | ✅ |
| `notification:broadcast` | ✅ | ❌ | ❌ |
| `settings:manage` | ✅ | ❌ | ❌ |
| `audit:view` | ✅ | ❌ | ❌ |

Adding "Sales" later means: insert `role = 'sales'`, insert `report:submit_sales` permission, map it, and register a `SalesReportDefinition` in the report-type registry (Section 3). No existing table or Server Action changes.

### 6.3 Permission Evaluation Order

1. **Middleware** — is there a valid session? If not, redirect to `/login`.
2. **Route-level guard** (layout-level, e.g., `/app/(hr)/layout.tsx`) — does the user hold *any* permission in this route group's required set? If not, 403 page.
3. **Service-layer check** — does the user hold the *specific* permission for this action? If not, throw `ForbiddenError`.
4. **Database RLS** — even if application logic is somehow bypassed, Postgres RLS policies (Section 8.4) independently enforce row-level access as the last line of defense.

## 7. Database Design

### 7.1 Conventions

- Every table: `id UUID PRIMARY KEY DEFAULT gen_random_uuid()`, `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`, `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()` (maintained via trigger), `deleted_at TIMESTAMPTZ NULL` for soft delete.
- Soft delete: application queries always filter `deleted_at IS NULL` via Prisma middleware; hard delete is restricted to a scheduled retention job (Section 13.7).
- Foreign keys use `ON DELETE RESTRICT` by default, `ON DELETE CASCADE` only for strictly dependent child rows (e.g., `teacher_classes` rows under a `teacher_reports` row).
- Naming: snake_case columns/tables (Postgres convention), camelCase in Prisma models (Prisma handles the mapping via `@map`/`@@map`).

| `users` | Mirrors Supabase `auth.users` id; app-level identity anchor |

### 7.5 Prisma Model Architecture

Prisma models mirror the tables above 1:1, organized into separate schema files stitched via `prisma.config` (`prisma/schema/*.prisma` with `previewFeatures = ["prismaSchemaFolder"]`) so the schema scales cleanly as departments are added:

```
prisma/schema/
  identity.prisma      // User, Profile, Role, Permission, RolePermission, UserRole
  employee.prisma       // Employee, Department, Attendance, Holiday
  reports.prisma         // TeacherReport, TeacherClass, MarketingReport, MarketingMeeting, MarketingCall
  crm.prisma              // MarketingLead, MarketingFollowup, MarketingDeal
  leave.prisma            // LeaveRequest
  system.prisma           // Notification, AuditLog, ActivityLog, Settings
```

Example excerpt (`employee.prisma`):

```prisma
model Employee {
  id                   String   @id @default(uuid())
  employeeCode         String   @unique @map("employee_code")
  departmentId         String   @map("department_id")
  designation          String
  joinDate             DateTime @map("join_date") @db.Date
  employmentStatus     String   @default("active") @map("employment_status")
  reportingManagerId   String?  @map("reporting_manager_id")

  department           Department @relation(fields: [departmentId], references: [id])
  reportingManager     Employee?  @relation("ManagerReports", fields: [reportingManagerId], references: [id])
  directReports        Employee[] @relation("ManagerReports")

  attendance           Attendance[]
  leaveRequests        LeaveRequest[]
  teacherReports       TeacherReport[]
  marketingReports     MarketingReport[]

  createdAt            DateTime  @default(now()) @map("created_at")
  updatedAt            DateTime  @updatedAt @map("updated_at")

```

Prisma Client is wrapped in a **soft-delete middleware** (`$extends`) so every model with a `deletedAt` field automatically excludes soft-deleted rows unless a query explicitly opts in with `includeDeleted: true`.

## 8. Authentication & Authorization

### 8.1 Authentication Flow

- Supabase Auth handles email/password sign-in, email verification, and password reset out of the box.
- On successful sign-in, Supabase issues a JWT (access token) + refresh token, stored in **httpOnly, secure cookies** via `@supabase/ssr`'s cookie adapter — never in `localStorage`.
- Next.js **Middleware** runs on every request to refresh the session cookie and attach the resolved user to the request context.

```mermaid
flowchart LR
    A[User submits credentials] --> B[Supabase Auth verifies]
    B -->|success| C[JWT + refresh token issued]
    C --> D[Set httpOnly cookies via @supabase/ssr]
    D --> E[Middleware validates on each request]
    E --> F{Session valid?}
    F -->|yes| G[Attach user + roles to request]
    F -->|no| H[Redirect to /login]
```

### 8.2 Email Verification & Password Reset

- New employees are created by HR via a Server Action that calls `supabase.auth.admin.inviteUserByEmail()`, sending a Supabase-hosted invite email; the employee sets their password on first login.
- Password reset uses `supabase.auth.resetPasswordForEmail()`, landing on a dedicated `/reset-password` route that verifies the recovery token before allowing a new password (Zod-validated for strength).

### 8.3 Route Protection

- `middleware.ts` matches all routes except static assets and `/login`, `/reset-password`.
- Route groups encode required permission sets: `/app/(hr)/**`, `/app/(teacher)/**`, `/app/(marketing)/**`, with a shared `/app/(shared)/**` for profile/notifications.
- Each route group's `layout.tsx` performs the Section 6.3 step-2 guard server-side (before any UI renders), preventing any flash-of-protected-content.

### 8.4 Row Level Security (RLS) Strategy

RLS is **defense-in-depth**, not the primary authorization mechanism (that's the service layer) — but it is mandatory on every table so a bug in application code cannot leak data.

General pattern:

```sql
alter table public.leave_requests enable row level security;

-- Employees can see their own leave requests
create policy "employees_select_own_leave"
on public.leave_requests for select
using (employee_id = auth.uid());

-- HR (or anyone holding leave:approve) can see and update all
create policy "hr_manage_all_leave"
on public.leave_requests for all
using (
  exists (
    select 1 from user_roles ur
    join role_permissions rp on rp.role_id = ur.role_id
    join permissions p on p.id = rp.permission_id
    where ur.user_id = auth.uid()
      and p.name = 'leave:approve'
  )
);
```

This same `has_permission(auth.uid(), 'permission:name')` check is wrapped as a Postgres **SQL function** (`security definer`) and reused across every policy to avoid duplicating the join logic per table:

```sql
create or replace function has_permission(uid uuid, perm text)
returns boolean
language sql security definer stable as $$
  select exists (
    select 1 from user_roles ur
    join role_permissions rp on rp.role_id = ur.role_id
    join permissions p on p.id = rp.permission_id
    where ur.user_id = uid and p.name = perm
  );
$$;
```

Policies then read as `using (has_permission(auth.uid(), 'employee:view_all') or employee_id = auth.uid())`.

### 8.5 How Auth, Authorization, and DB Permissions Compose

| Layer | Question it answers | Mechanism |
|---|---|---|
| Authentication | "Who are you?" | Supabase Auth JWT, verified in Middleware |
| Route Guard | "Can you even be here?" | Layout-level permission-set check |
| Authorization (service) | "Can you do *this specific action*?" | `hasPermission(user, 'resource:action')` in service layer |
| RLS (DB) | "Even if everything above is bypassed, can this SQL statement touch this row?" | Postgres policies using `has_permission()` |

All four layers must agree; RLS is intentionally the strictest and final gate.

### 9.3 Key Interaction: Employee Creation

1. HR opens "Add Employee" drawer → React Hook Form + Zod schema (`employeeCreateSchema`).
2. On submit, Server Action `createEmployee()`:
   - Validates payload server-side (never trusts client validation alone).
   - Calls `supabase.auth.admin.inviteUserByEmail()`.
   - Creates `users`, `profiles`, `employees`, `user_roles` rows in a single Prisma `$transaction`.
   - Writes an `audit_logs` entry (`action = 'employee.create'`).
   - Writes a `notifications` row for the new employee's manager (if set).
3. `revalidatePath('/hr/employees')`; UI shows optimistic row + toast; skeleton while confirming.

### 12.1 Visual Direction

Inspired by Linear, Notion, Stripe Dashboard, Vercel Dashboard, and GitHub: dense-but-breathable information design, restrained color (neutral grays + one accent), subtle elevation via shadow rather than heavy borders, generous use of monospace for codes/IDs, and motion that clarifies state changes rather than decorating them.

## 13. Security Architecture

| Concern | Mitigation |
|---|---|
| OWASP A01 Broken Access Control | 4-layer authorization (Section 8.5); RLS on every table |
| OWASP A02 Cryptographic Failures | TLS everywhere (Vercel/Supabase enforced); secrets never in client bundle |
| OWASP A03 Injection | Prisma parameterizes all queries; zero raw string SQL concatenation; Zod validates all input shape/type before it reaches Prisma |
| XSS | React's default escaping; no `dangerouslySetInnerHTML` except for a sanitized (DOMPurify) rich-text renderer if notes support formatting |
| CSRF | Server Actions use Next.js's built-in origin-checking; state-changing Route Handlers require same-site cookies + explicit origin header check |
| File Upload Security | File type allow-list, size limits, virus-scan hook placeholder, storage bucket policies (Section 14) |
| Secrets Management | All keys in Vercel Environment Variables (per-environment: dev/preview/prod); `SUPABASE_SERVICE_ROLE_KEY` used **only** in trusted server contexts, never exposed to client |
| Audit Logging | Immutable `audit_logs` table (Section 7.4), DB-level `REVOKE UPDATE, DELETE` |
| Rate Limiting | Vercel Edge Middleware + Supabase built-in Auth rate limits on login/reset endpoints |
| Data Retention | Soft-deleted rows purged by a scheduled job only after a configurable retention window, itself audit-logged |

### 13.1 Environment Variables (representative)

| Variable | Scope |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Public |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Public (RLS-protected, safe to expose) |
| `SUPABASE_SERVICE_ROLE_KEY` | Server-only, never `NEXT_PUBLIC_` |
| `DATABASE_URL` / `DIRECT_URL` | Server-only, Prisma connection (pooled + direct for migrations) |
| `RESEND_API_KEY` or SMTP creds (if custom email needed beyond Supabase Auth emails) | Server-only |

## 14. File Storage Design

| Bucket | Contents | Access Policy |
|---|---|---|
| `profile-photos` | Employee avatars | Public read (via signed/public URL), write restricted to the owning user or HR |
| `employee-documents` | Offer letters, ID proofs, contracts | Private; read/write restricted to HR (`employee:edit`) and the owning employee for their own docs |
| `leave-attachments` | Medical certificates etc. attached to leave requests | Private; read restricted to the requester and anyone with `leave:approve` |
| `report-attachments` | Teacher "notes uploaded" files, marketing collateral | Private; read/write scoped to report owner + HR |

All non-public buckets use Supabase Storage policies mirroring the RLS pattern in 8.4 (`has_permission()` reused), and files are referenced in Postgres by **path only** (never by public URL) — read access is brokered through short-lived **signed URLs** generated server-side at render/download time.

## 15. Realtime Notifications

### 15.1 Delivery Mechanism

`notifications` table insert → Supabase Realtime (Postgres CDC via logical replication) → client subscribes to a **per-user filtered channel** (`notifications:employee_id=eq.<uid>`) → toast + notification-bell badge update, no polling.

```mermaid
sequenceDiagram
    participant SVC as Service Layer
    participant DB as notifications table
    participant RT as Supabase Realtime
    participant UI as Recipient Browser

    SVC->>DB: INSERT notification (recipient, type, payload)
    DB-->>RT: Change event (CDC)
    RT-->>UI: Push via WebSocket (subscribed channel)
    UI->>UI: Update bell badge + optional toast
```

### 15.2 Notification Types

| Type | Trigger | Recipient(s) |
|---|---|---|
| `leave.approved` / `leave.rejected` | HR decision on a leave request | Requesting employee |
| `leave.requested` | Employee submits leave | HR holders of `leave:approve` |
| `report.reminder` | Scheduled job (e.g., 6 PM) if no report submitted | Employee who hasn't reported |
| `employee.created` | New employee onboarded | HR team, new employee's manager |
| `announcement` | HR broadcast composer | Targeted role/department, or org-wide |
| `system.alert` | Operational issues (rare, admin-triggered) | HR Admins |

Scheduled notifications (e.g., report reminders) are generated by a **Vercel Cron** job hitting a protected Route Handler that queries for employees without a report for the current date and inserts `notifications` rows — Realtime delivery is identical to the direct-insert path.

### 16.2 Query Optimization Strategy

- **Materialized Postgres views** for expensive aggregations that don't need to-the-second freshness (e.g., `mv_monthly_department_attendance`), refreshed via a nightly Vercel Cron → Route Handler → `REFRESH MATERIALIZED VIEW CONCURRENTLY`.
- **Indexed date columns** (`attendance_date`, `report_date`, `closed_at`) on all reporting tables — every analytics query filters by a date range first.
- **Partial indexes** for common filters, e.g. `CREATE INDEX ON leave_requests (status) WHERE status = 'pending'` to keep the HR approval queue query fast regardless of historical leave volume.
- Heavy dashboard queries are executed via **Prisma raw SQL** (`$queryRaw`) against the views/indexes above rather than doing aggregation in application code — push computation to Postgres.
- Recharts components receive **pre-aggregated** data from Server Components (fetched via the service/repository layer), never raw row-level data shipped to the client.

## 17. Deployment Architecture & CI/CD

### 17.1 Environment Flow

```mermaid
flowchart LR
    Dev["Local Dev\n(Next.js + local Supabase CLI)"] -->|git push branch| GH[GitHub]
    GH -->|PR opened| CI["GitHub Actions CI\n(lint, typecheck, unit, Playwright)"]
    CI -->|pass| PV["Vercel Preview Deployment\n+ Supabase branch DB"]
    PV -->|reviewed & merged to main| PROD["Vercel Production Deployment"]
    PROD --> SUPA["Supabase Production Project"]
```

### 17.2 Local Development

- Supabase CLI (`supabase start`) runs a local Postgres + Auth + Storage stack in Docker, mirroring production.
- `prisma migrate dev` applies migrations locally; `prisma db seed` loads roles/permissions/demo data.
- `.env.local` holds local Supabase URL/keys; never committed (`.gitignore`).

### 17.3 Preview Deployments

- Every PR triggers a Vercel Preview build **and** a corresponding Supabase preview branch (Supabase's database branching), so each PR gets an isolated database matching the PR's migration state — no shared staging drift.

### 17.4 Production Deployment

- Merge to `main` triggers Vercel production build.
- `prisma migrate deploy` runs as a build step (or a gated GitHub Actions job before deploy) against the production `DIRECT_URL`, applying only already-reviewed migration files.
- Migrations are **additive-first**: destructive changes (drop column, etc.) ship in a follow-up release after the code no longer references the old shape, avoiding downtime.

### 17.5 CI/CD Pipeline (GitHub Actions)

| Stage | Action |
|---|---|
| Lint & Typecheck | `eslint`, `tsc --noEmit` |
| Unit/Component Tests | `jest` + React Testing Library |
| E2E Tests | `playwright test` against a Preview Deployment URL |
| Migration Check | `prisma migrate diff` to catch drift between schema and migration files |
| Deploy | Vercel auto-deploys on merge (native GitHub integration); Actions gate the merge, not the deploy itself |

### 17.6 Rollback Strategy

- Vercel: instant rollback to any previous production deployment via the dashboard/CLI (atomic, no rebuild needed).
- Database: because migrations are additive-first, a code rollback rarely requires a DB rollback; when a schema rollback is unavoidable, a paired "down" migration is authored and reviewed before the risky migration ships.

### 17.7 Backup Strategy

- Supabase automated daily backups (Point-in-Time Recovery on paid tiers) for the production project.
- Weekly `pg_dump` exported to a separate storage location as an out-of-band backup, retained on a rolling 90-day window.
